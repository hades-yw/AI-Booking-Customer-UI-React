# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Rservo — a multi-route React + TypeScript app for browsing local service merchants and booking appointments: landing/search → merchant detail → date & time → customer details → checkout → confirmation. Built with Vite, React Router, and Tailwind CSS v4. Responsive from mobile up through desktop.

This is the React rebuild of the customer-facing booking web experience and is now the **sole active customer-facing frontend** for `../AI-Booking-System`. The sibling Flutter app `../AI-Booking-Customer-UI` is paused as of 2026-09-01 — do not reference or extend it; all customer-facing frontend work happens here.

**API wiring** — check `src/api/index.ts` before assuming mock vs. live:
- Tenant browsing (`getCategories`, `getMerchants`, `getMerchant`), availability (`getAvailability`, `getAvailabilityForDate`, `getStaff`, `getAvailabilityByStaff`), pricing (`getQuote`), booking creation (`createBooking`, `uploadPaymentReceipt`), and auth (`register`, `login`, `getMe`, `updateProfile`, `forgotPassword`, `resetPassword`) are all **live** against the real backend via `httpApiClient` (`src/api/httpClient.ts`), driven by `VITE_API_BASE_URL` in `.env` (defaults to `http://localhost:8000/v1` locally — the backend must be running). Auth hits `/v1/auth/register`, `/v1/auth/login`, `/v1/auth/me`, `/v1/auth/forgot-password`, `/v1/auth/reset-password`, and `/v1/customers/me` (PATCH) — `register`'s `RegisterPayload` (`{name,email,password}`) omits `tenant_id`, so the backend auto-assigns `role: customer` and creates a `CustomerProfile`; `login` returns only `{access_token}` (no refresh token — none exists on the backend), stored in `AuthContext` under `localStorage["rservo_token"]`.
- `createBooking(payload, token?)` takes an optional auth token as its second argument — `CheckoutPage.tsx` pulls it from `useAuth()` and passes it through so the backend can link the booking to the logged-in customer's `CustomerProfile` via `customer_id` (see the backend's `create_guest_booking` in `app/routes/booking.py`). Without it, a booking made while logged in still succeeds but silently lands as an unlinked guest booking and never shows up under "My Bookings" — this was a real bug (fixed 2026-09-01) where the token simply wasn't being threaded through on this one call, unlike the other authenticated `ApiClient` methods which all take `token` explicitly. If adding a new authenticated write, follow this same explicit-`token`-parameter pattern rather than relying on a shared client to attach it implicitly.
- `mockApiClient` (`src/api/mockClient.ts`) still exists as a parallel implementation (localStorage-backed fake users, no network) but is not imported by `index.ts` — swap it in only if you need to work fully offline from the backend.
- `src/api/index.ts` exports a single `api` const — check which client it points to before debugging "why doesn't this show my mock data" or "why is this 404ing against localhost:8000".

### Checkout, pricing, and coupons
`createBooking` posts to the real `POST /v1/public/bookings/{tenant_slug}` endpoint with the backend's `MultipleSlotBookingCreate` shape (`slots: [{ start_time, duration_minutes, service_id, package_id, option_ids, staff_id }]`, `coupon_code`, `guest_name`/`guest_phone`) and returns the real `BookingResponse` mapped down to `BookingConfirmation`. Two things to know before touching this:

- **Both "By Date" and "By Staff" schedule modes populate `SelectedSchedule.startTime`/`endTime`.** `DayAvailability.slots` (backing "By Date" mode) is `TimeSlot[]`, same as `StaffDayAvailability.slots` — both `getAvailability`/`getAvailabilityForDate` and `getAvailabilityByStaff` preserve the backend's raw `start_time`/`end_time` alongside the display `label`, and `BookingPage.tsx`'s `handleProceed` sets `startTime`/`endTime` in both branches. `ConfirmationPage`/`CheckoutPage` still guard on `schedule.startTime` before calling `getQuote`/enabling the coupon input/`createBooking`, but this is now just a defensive fallback (it should always be truthy) rather than a real mode split — don't reintroduce a `string[]`-only slot shape for either mode, since that's what previously broke this.
- **`pkg.total` is a display estimate, not the charged amount.** The backend can price a service/package/option with `pricing_basis: "per_hour"` (scaled by `duration_minutes / 60` in `app/utils/pricing.py::price_for_basis` on the backend), which `pkg.total`'s flat additive sum doesn't account for — and peak-pricing rules can adjust it further. `ConfirmationPage` calls `api.getQuote` as soon as a `startTime` is available (before any coupon is applied) and stores the result in `BookingFlowContext.quote`; both `ConfirmationPage` and `CheckoutPage` display `quote.totalAmount`/`quote.subtotal` when a quote is present, falling back to `pkg.total` only if the quote call hasn't resolved yet or isn't supported. Never reintroduce a client-side "recompute the total from pkg" for money actually charged — always prefer the server quote. `BookingPage.tsx` itself also fires its own local `api.getQuote` call (no coupon, not stored in `BookingFlowContext`) as soon as a time slot is picked in either mode, purely so its sticky `PackageSummaryCard` sidebar can show a real total (`quoteLoading` → "Calculating…", then the resolved amount) instead of sitting on the flat `pkg.total` estimate for the whole schedule step — this is a separate, page-local quote fetch, not shared state with `ConfirmationPage`'s.
- **`Quote.lines` carries the server's real per-item breakdown** (`{type: "service"|"package"|"option", name, amount, pricingBasis: "per_hour"|"flat"}[]`, mapped from the backend quote response's `lines` array in `httpClient.ts`'s `toQuote`). These `amount`s are already `pricing_basis`-scaled (e.g. a per-hour service/package doubled for a 120-minute booking) — they are what the itemized rows must sum to reach `subtotal`, unlike `pkg.selectedPackages[].price`/`pkg.selectedOptions[].price`, which are the flat unscaled catalog prices. `BookingPage.tsx`'s `PackageSummaryCard` has a "How is this calculated?" toggle that itemizes `quote.lines` (falling back to the flat `pkg.price`/`selectedPackages`/`selectedOptions` estimate only when no quote has resolved yet). **A scaled `amount` alone reads as a mystery number** — showing "RM1000" for a service catalogued at "RM500/hr" with no explanation of where the 2x came from is confusing (this is exactly what a past version of this breakdown did and had to be corrected). For each `pricingBasis: "per_hour"` line, `PackageSummaryCard` derives and displays the rate as a sublabel: `line.amount / (quote.billableDurationMinutes / 60)` formatted as "RM500/hr × 2hr", plus a one-line note above the itemized rows when any line is per-hour. Don't drop that sublabel when touching this component — the raw scaled total by itself is the exact confusion this was added to prevent. `mockApiClient.getQuote` returns `lines: []` (mock has no per-item visibility) — any breakdown UI must handle an empty-lines quote by falling back to the estimate, not assume `lines` is always populated. `ConfirmationPage`/`CheckoutPage` also itemize via `quote.lines` now (each page defines its own local `QuoteLineRow`/`hoursLabel`, not shared with `BookingPage.tsx`'s `BreakdownRow` since that one is styled for the dark gradient card) — falling back to the flat `pkg.selectedPackages`/`selectedOptions` prices only when no quote has resolved yet, same rule as `PackageSummaryCard`. `CheckoutPage`'s Order Summary previously collapsed everything into one `pkg.name` subtotal row even with a quote present (masking the real breakdown) — it now lists `quote.lines` directly, same as the other two pages. If asked to touch pricing display again, prefer factoring the three near-duplicate `QuoteLineRow`/`hoursLabel` implementations (`BookingPage.tsx`, `ConfirmationPage.tsx`, `CheckoutPage.tsx`) into one shared component rather than adding a fourth copy.
- **Local-naive → UTC conversion** happens in `httpClient.ts`'s `localNaiveToUtcIso`, using the tenant's IANA timezone now exposed as `Merchant.timezone` (mapped from the backend's `Tenant.timezone` field, added to `TenantBase`/`TenantCardResponse` in the backend's `app/schemas/tenant.py` — previously that column existed on the model but wasn't exposed in any schema). Both `getQuote` and `createBooking` require `tenantTimezone` in their call payload for this reason.
- **Coupons have no public lookup/validate endpoint** — "applying" a coupon (`CouponInput`, `src/features/booking/CouponInput.tsx`) means calling `api.getQuote` with the code and trusting the server's 400 (`{"detail": "..."}`, e.g. "Invalid coupon code", expired, usage-limit-reached, minimum-not-met) or success. A successful quote is stored via `BookingFlowContext.setCoupon(code, quote)`; changing the schedule (`setSchedule`) or starting a new booking (`startBooking`) clears both, since a quote is only valid for the start_time/duration it was computed against.
- **Multiple checked packages collapse to one on submit.** The backend's per-slot booking model supports one `package_id` (plus a list of `option_ids`) — it has no representation for "two packages checked simultaneously" the way the frontend's additive checkbox UI allows (see the Pricing model section below). `createBooking` sends only `pkg.selectedPackages[0]`'s id as the slot's `package_id`; this matches the common case (0-1 package checked) but under-charges if a customer checks multiple packages. Fixing this properly would mean either changing the backend to accept multiple packages per slot, or splitting into multiple slots (which would double-count `service.price` per `calculate_quote` — see `app/utils/pricing.py`) — not attempted here.
- **Payment is QR-scan + receipt upload, not a gateway.** There's no public payment-gateway endpoint. After `createBooking` succeeds, `CheckoutPage`'s success screen shows `merchant.qrCodeImage` (mapped from `Tenant.qr_code_image`, uploaded by the merchant via the authenticated `POST /v1/upload/tenant_qr_code`) for the guest to scan and pay manually, then lets them upload a receipt image via `api.uploadPaymentReceipt` → `POST /v1/public/upload/{tenant_slug}/payment-receipt/{booking_id}` (PNG/JPEG only, 5MB limit). The merchant later reviews and approves the booking from the admin side (`PATCH /v1/bookings/{booking_id}/status`), which also flips the associated `Payment.status` to `paid`. `PaymentMethodPicker` (card/wallet) is still shown on `CheckoutPage` as a stated preference, but no payment API call is made for it — it's not wired to anything on the backend.

## Architecture

### API boundary
All data access goes through `src/api/index.ts`, which exports a single `api` object typed by the `ApiClient` interface in `src/api/client.ts`. Two implementations exist side by side — `mockApiClient` (`src/api/mockClient.ts`, serving `src/api/mockData.ts`) and `httpApiClient` (`src/api/httpClient.ts`, hitting the real FastAPI backend) — see the wiring split noted above under Project Overview. No page or component needs to change when swapping which client `index.ts` exports; everything depends on the `ApiClient` interface, not its implementation. When adding a new data operation, add it to the `ApiClient` interface first, then implement it in both `mockClient.ts` and `httpClient.ts`.

`httpClient.ts` maps the backend's tenant payload onto this app's domain types (`tenantToMerchant`/`tenantCardToMerchant`) — this is where backend-shape assumptions live (e.g. `resolveAssetUrl` for relative upload paths, `hashString`-derived placeholder rating/tag/gradient since those aren't real backend concepts yet, `toServices` for the pricing hierarchy below).

### Pricing model: Service → Packages → Options (all additive checkboxes; only the service's price is mandatory)
The backend's `/v1/public/tenants/{slug}` payload nests pricing three levels deep — service, package, and option each carry their own independent `price`. **Only `service.price` is mandatory.** Packages and options are both **optional, multi-select checkboxes** — not a single required tier — so a customer can check zero, one, or several packages under a service, and zero or more options from whichever packages they checked:

```
total = service.price + Σ(checked package.price) + Σ(checked option.price)
```

This mirrors the backend (confirmed against `app/models/service.py` and `app/utils/pricing.py::calculate_quote` in `../AI-Booking-System`): `Service.price` is non-nullable and explicitly meant to stand alone ("per-hour pricing at service level if no packages involved"), while `package_id` is `Optional[int]` everywhere in the booking/pricing schemas — when absent, the backend quote is just the service price with no package line at all. Nothing at any level ever *replaces* the level above it; every checked box adds its price on top of the service's base price.

Concretely, for `frame-fern-photography`'s "Product Photography" service (`price: 500`): with nothing checked the total is **RM500** (service price alone). Checking the "Starter Product Set" package (`price: 500`) brings it to **RM1000**. Also checking the "Rush Delivery" option (`price: 150`, nested under that package) brings it to **RM1150**. A service can also have zero packages at all (e.g. a mock "Quick Chair Massage" at `price: 35` with `packages: []`), in which case it's just directly bookable for **RM35** with no drill-down. Never assume a package (or an option) is checked, or that a service has any packages to check in the first place.

Types (`src/types/index.ts`):
- **Service** — a category of offering, e.g. "Portrait Session". `price` is its own base price and the only field in this whole hierarchy that's guaranteed to exist and apply unconditionally. It's also literally the "From RMx" value shown on the collapsed card — there is **no separate `priceFrom` field** on `Service`; don't reintroduce one that bundles a package's price in "for display", since that misrepresents the true minimum a customer can pay (a past version of this code computed `priceFrom = price + cheapest package price`, which showed "From RM1000" for a service that's actually bookable from RM500 — the bug this section exists to prevent). `duration` is the fallback used when no package is checked. (`Merchant.priceFrom`, on the unrelated `Merchant` type, is a different field — the cheapest `service.price` across a merchant's services, used on `MerchantCard` for search/landing — that one's fine as-is.)
- **Package** (`ServicePackageTier`) — an optional, independently-checkable add-on tier within a service, e.g. "Studio Portrait". `packages: []` is valid and expected for some services. Multiple packages under the same service can be checked simultaneously — checking one does not uncheck another. Its `price` is additive on top of the service's `price`. Also carries `duration` (not in the real payload per-package — `httpClient.ts`'s `toServices` falls back to the tenant's `default_session_length`).
- **Option** (`ServiceOption`) — an add-on nested under a package, e.g. "Makeup Artist" — only offered once its parent package is checked, and disappears from the choices if that package is unchecked. `price` is additive on top of everything above it; multiple options can be checked per booking.

This hierarchy is presented via `ServiceAccordion` (`src/features/booking/ServiceAccordion.tsx`) on the Merchant Detail page's Packages tab. Each service card's price label is conditional on `hasDrilldown = service.packages.length > 0`: **"From {formatCurrency(service.price)}"** if the service has packages to drill into (since "From" implies there's a higher-priced path available once you check something), or just **"{formatCurrency(service.price)}"** with no "From" prefix if it has none (there's nothing to range "from" — that price is simply what it costs). Don't collapse this back to always showing "From" — a service with zero packages showing "From RM35" reads as if there's more to discover when there isn't.

If the service has packages, the card expands inline (one service at a time) into two checkbox sections — **Packages**, then **Add-ons** (built from `selectedPackages.flatMap(p => p.options)`, so it only lists options belonging to currently-checked packages and is empty until a package is checked). A live running total and one "Book Now" sit below both sections. If a service has zero packages, there's nothing to expand — the card shows the total (`service.price`) and "Book Now" directly on its own row, right below the (non-"From") price label. All the summation state and math lives in `ServiceCard` in that file (`selectedPackageIds`/`selectedOptionIds` as `Set<string>`, `total = service.price + packagesTotal + optionsTotal`) — **any future pricing bug is most likely here or in `httpClient.ts`'s `toServices`, since both must agree that every level below `service.price` is optional and additive, never mutually exclusive or auto-applied.**

Once "Book Now" is clicked, the current selection collapses into a single `ServicePackage` — the flat shape that flows through `BookingFlowContext` and the rest of the booking flow (`/book` → `/confirm` → `/checkout`). Its fields:
- `price` — `service.price` alone (NOT including any checked packages — see `total` for that).
- `selectedPackages` — the `ServicePackageTier[]` the customer checked (possibly more than one, possibly empty).
- `selectedOptions` — the `ServiceOption[]` the customer checked across all checked packages (empty if no package was checked).
- `total` — `price` + sum of `selectedPackages` prices + sum of `selectedOptions` prices. **This is the amount actually charged** — always display `pkg.total`, not `pkg.price`, wherever a page shows what the customer is paying (sticky headers, order summaries, confirmation totals). `pkg.price` alone is only the service's own base rate before any checkboxes.

When adding a new page/component that touches booking totals, grep for `pkg.total` usage in `BookingPage.tsx`/`ConfirmationPage.tsx`/`CheckoutPage.tsx` for the pattern (base row + itemized `selectedPackages` rows + itemized `selectedOptions` rows + total row). When adding a new service/package mapping (mock or real), double-check the additive formula above — every level is opt-in on top of `service.price`, none of them are ever assumed-selected or mutually exclusive.

### Schedule step: "By Date" vs "By Staff" (`BookingPage.tsx`)
The date & time step (`/merchants/:id/book`) supports two modes, toggled via `ModeToggle` (`src/features/booking/ModeToggle.tsx`):
- **By Date** (default) — staff-agnostic, unchanged from the original flow. `api.getAvailability(merchantId, packageId)` prefetches a 7-day `DayAvailability[]` grid up front; `api.getAvailabilityForDate` fetches an arbitrary date picked from `CalendarPanel`.
- **By Staff** — `api.getStaff(merchantId)` lists staff (`Staff[]`); `StaffPicker` (`src/features/booking/StaffPicker.tsx`) lets the customer pick one or "Any staff" (`staffId: null`). `api.getAvailabilityByStaff(merchantId, packageId, date)` returns **all** staff's slots for **one date**. Like "By Date" mode, staff mode prefetches a 7-day quick-pick strip up front (one `getAvailabilityByStaff` call per date, via `Promise.all`) and also supports picking an arbitrary date beyond that strip via `CalendarPanel` — picking a date outside the 7-day window stores it in `customStaffDay` state (mirroring `customDay` in "By Date" mode) and fetches it on demand with a single `getAvailabilityByStaff` call, rather than extending the prefetched array. "Any staff" shows the **union** of every staff member's available slot labels for that date.

The toggle only renders when `getStaff` returns a non-empty list — some tenants have no staff configured at all (the backend seed's `shine-auto-detailing` tenant is deliberately staff-less for testing this). Both modes reuse the same `DateStrip`/`TimeSlotGrid`/`CalendarPanel` components (`src/features/booking/`) and both feed them the same `DayAvailability`/`{date, slots: TimeSlot[]}` shape — staff mode dedupes the per-staff (or "Any staff" union) slots down to one `TimeSlot[]` by label, rather than using a different shape for date vs. staff mode.

`TimeSlotGrid` (`src/features/booking/TimeSlotGrid.tsx`) shows each slot's end time as a sublabel under its start time (e.g. "10:00 AM – 12:00 PM"), formatted via `formatLocalNaiveTime` (`src/lib/date.ts`) applied to `slot.endTime` — **never derive it from `pkg.duration` added to the start time**, since per-slot duration isn't guaranteed uniform across a grid (a service's session length can vary, and this is the one place duration is visible before the customer commits to a slot; without it, a jump like RM500→RM1000 in the summary card once a slot is picked has no visible cause). `formatLocalNaiveTime` is the shared tenant-local-naive time formatter (moved here from `httpClient.ts`'s now-aliased `formatSlotLabel`) — reuse it for any other UI that needs to print a `TimeSlot`/`SelectedSchedule` time field; never format those with `new Date(iso)` (see the Email links/Availability endpoints sections above for why).

Selecting a slot in either mode calls `setSchedule` (`BookingFlowContext`) with a `SelectedSchedule` — `{date, slot, startTime, endTime}` always, plus optional `staffId`/`staffName` when set in staff mode. `ConfirmationPage`/`CheckoutPage` render a "Staff" row only when `staffName` is present. **`startTime`/`endTime` on `TimeSlot`/`SelectedSchedule` are tenant-local naive ISO strings as returned by the backend (see the backend CLAUDE.md's Availability endpoints section) — never fed through `new Date(iso)` for display (that would apply the browser's own timezone on top); `httpClient.ts`'s `formatSlotLabel` parses the clock-time portion directly instead.** `getQuote`/`createBooking` convert these to UTC via `localNaiveToUtcIso` before submitting, for either mode.

### Directory layout
```
src/
  api/            # ApiClient contract + mock/http implementations
  types/          # Shared domain types (Merchant, Service/ServicePackageTier/ServiceOption, ServicePackage, Booking…)
  lib/            # Formatting/date helpers (date.ts, style.ts), useAsync data-fetching hook
  context/        # AuthContext, BookingFlowContext, FavoritesContext
  components/
    ui/           # Generic primitives: Button, Card, TextField, StepProgress…
    layout/       # Page shell pieces: TopNav, BottomActionBar, PageContainer
  features/
    merchants/    # Merchant card/grid/category filter
    booking/      # Service→package→options accordion, date strip, time slot grid, staff picker, mode toggle, payment picker
  pages/          # One component per route
  routes.tsx      # Route table (React Router)
  App.tsx         # Providers + router outlet
```

### State/context
- `BookingFlowContext` holds the in-progress booking for the duration of the booking flow only: the selected `ServicePackage` (already resolved per the pricing model above — the base service plus whichever packages and options were checked, and the resulting total), schedule, customer details, and payment method. It is not persisted server-side: directly linking to or refreshing `/checkout` without completing the earlier steps redirects to the landing page, since there's no session to restore it from.
- `FavoritesContext` holds favorited merchants in-memory, per session (not persisted).
- `AuthContext` holds auth/session state, backed by the `ApiClient` auth methods (`login`, `register`, `getMe`, `updateProfile`, `forgotPassword`, `resetPassword`).

### Routes (`src/routes.tsx`)
`/` (landing/search) → `/merchants/:merchantId` → `/merchants/:merchantId/book` → `/merchants/:merchantId/checkout` → `/merchants/:merchantId/confirm`, plus `/login`, `/register`, `/forgot-password`, `/reset-password`, `/profile`, and a catch-all 404.
